구현 작업을 한 번에 몰아치지 않고 **작은 단계로 쪼개어** 진행한다. 각 단계는 검증으로 끝나고,
보고는 완료분과 예정분을 눈으로 구분할 수 있게 쓴다.

**코드를 쓰는 것은 코덱스, 설계·검증·검토·보고는 클로드**가 맡는다 (→ 3단계).

`$ARGUMENTS`가 있으면 그 작업을, 없으면 진행 중이던 작업을 이 방식으로 이어간다.

## 이 모드를 쓰는 이유

큰 덩어리로 진행하면 세 가지가 무너진다.

- 어디까지가 검증된 코드인지 흐려진다
- 설계 판단이 필요한 지점을 지나쳐 놓고 나중에 발견한다
- 보고가 길어져 "무엇이 끝났고 무엇이 남았는지"가 안 보인다

## 단계 크기

한 단계는 **파일 몇 개 ~ 한 계층**이다. 기준은 "검증 한 번으로 옳고 그름이 갈리는가"다.

| 적절 | 과함 |
| --- | --- |
| 값 객체 3개 + 테스트 | 도메인 전체 |
| Repository + Fake + 매핑 테스트 | 데이터 계층 전부 |
| 화면 하나의 상태·UiModel | 화면 5개 |

각 단계 끝에는 **실행 가능한 검증**이 있어야 한다. 빌드, 테스트, 실행 중 하나. 검증이 없으면
단계를 잘못 쪼갠 것이다.

## 진행 절차

```
[1] 다음 단계 예고 → [2] 승인 → [3] 구현(코덱스) → [4] 검증 → [5] 보고 → [6] 미결정 해소 → [7] 커밋
                                                                              ↓
                                                                          [1] 로 반복
```

### 1. 다음 단계 예고

무엇을 만들지 **먼저** 보여준다. 만들 파일 목록과 핵심 코드 스케치, 그 단계에서 함께 검증되는
불확실한 것을 적는다.

이 예고가 3단계에서 코덱스에 넘길 스펙이 된다. 사용자가 읽고 판단할 수 있으면서, 맥락 없는
에이전트가 그것만 보고 구현할 수 있을 만큼 적는다.

### 2. 승인

사용자가 "계속"이라고 하면 진행한다. 사용자가 리듬을 지정했으면(파일 하나씩 / 단계마다 /
큰 덩어리) 그것을 끝까지 지킨다.

### 3. 구현 (코덱스에 위임)

**파일을 만들고 고치는 일은 `codex exec` 가 한다.** 클로드가 직접 코드를 쓰지 않는다.
1단계에서 예고한 스펙을 그대로 stdin 으로 넘긴다.

```bash
codex exec -C <프로젝트 루트> --sandbox workspace-write --approve-for-me - <<'SPEC' 2>&1 | tail -40
<1단계 예고 그대로: 고칠 파일, 만들 타입/함수 시그니처, 지켜야 할 기존 규약, 범위 밖>
SPEC
```

코덱스는 이 대화의 맥락을 **하나도 못 받는다.** 스펙에 다음이 없으면 엉뚱한 걸 만든다.

- 고칠 파일의 경로와, 기존 코드에서 따라야 할 규약 (네이밍, 계층, 쓰는 라이브러리)
- 만들 타입·함수의 시그니처
- **건드리면 안 되는 범위**

돌아오면 `git diff` 로 **직접 읽고 검토한다.** 코덱스가 "했다"고 한 말을 믿지 않는다. 스펙과
다르거나 범위를 넘었으면 그 자리에서 되돌리고 스펙을 고쳐 다시 시킨다.

예고한 범위만 만들게 한다. 하다가 범위 밖이 필요해지면 멈추고 보고한다. 조용히 넓히지 않는다.

#### 위임하지 않는 것

스펙 쓰는 비용이 코드 쓰는 비용보다 크면 클로드가 직접 고친다.

- 한 줄 수정, 오타, 시그니처 변경에 따른 호출부 정리
- 코덱스 결과를 검토한 뒤의 미세 교정
- 코덱스가 두 번 연속 스펙을 못 맞춘 지점 (세 번째는 직접 하고, 왜 안 됐는지 보고에 적는다)

### 4. 검증

빌드나 테스트를 **실제로 돌린다**. 통과 여부를 추측하지 않는다. 실패하면 그 단계는 끝나지 않은
것이다.

### 5. 보고

아래 형식을 지킨다. 구분선과 이모지로 완료분과 예정분을 갈라 놓는 것이 핵심이다.

```markdown
---
# ✅ 완료: <단계 이름> (N단계)

## 만든 파일

| 파일 | 내용 |
| --- | --- |
| `경로` | 한 줄 설명 |

## 검증 결과

​```
테스트 N개 통과
​```

## 알아낸 것

문서·설계와 달랐던 사실, 빌드하며 발견한 함정. 없으면 이 절을 생략한다.

## 확인이 필요한 결정

이 단계에서 새로 생긴 미결정 사항. 없으면 "없음"이라고 쓴다.

---
# ⏭️ 다음: <단계 이름> (N+1단계)

## 만들 파일

| 파일 | 내용 |
| --- | --- |

## 핵심

코드 스케치 몇 줄.

## 함께 검증되는 것

이 단계로 확인될 불확실한 항목.
```

### 6. 미결정 해소 (필수)

**"확인이 필요한 결정"이 있으면 다음 단계로 넘어가기 전에 해소한다.** 쌓아두지 않는다.

해소는 반드시 `AskUserQuestion` 으로 한다. 산문으로 묻고 답을 기다리지 않는다.

질문을 만들 때:

- 선택지마다 `preview` 에 **실제 코드나 화면 모양**을 넣는다. 추상적 설명만으로는 못 고른다
- 무엇이 달라지는지를 적는다. 장단점 나열이 아니라 "이걸 고르면 이 코드가 이렇게 된다"
- 추천안을 첫 번째에 두고 `(추천)` 을 붙인다
- 감수해야 할 손실이 있으면 숨기지 않는다

답이 나오면 **코드와 문서에 함께 반영한다.** 코드만 고치고 설계 문서를 놔두면 다음에 문서를
믿고 잘못 만든다.

### 7. 커밋

한 단계가 검증까지 끝나면 그 시점에 커밋한다. 롤백 단위를 단계와 일치시킨다.

커밋 메시지 본문에는 **무엇을 왜**와 함께, 그 단계에서 **알아낸 사실**을 남긴다. 다음 사람이
같은 함정에 빠지지 않게 한다.

## 코덱스 사전 세팅 (한 번만)

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 설치 확인 | `codex --version` | 없으면 위임 불가. 그 사실을 먼저 보고하고 직접 구현으로 전환한다 |
| 권한 허용 | 전역 `settings.json` 의 `permissions.allow` 에 `Bash(codex exec:*)` | 단계마다 승인 프롬프트가 뜨는 것을 막는다 |
| 샌드박스 | `--sandbox workspace-write` | 기본값 `read-only` 로는 파일을 못 쓴다 |
| 승인 | `--approve-for-me` | `exec` 는 비대화형이라 승인 요청이 오면 그대로 멈춘다 |
| 작업 루트 | `-C <프로젝트 루트>` | 클로드의 cwd 와 무관하게 고정한다 |
| 출력 | `2>&1 \| tail -40` | 코덱스 쪽 훅 로그·MCP 경고가 섞여 나온다 |
| git 아닌 경우 | `--skip-git-repo-check` | 다만 검토를 `git diff` 로 하므로 git 저장소를 권한다 |

오래 걸리는 단계는 `run_in_background` 로 던지고, 기다리는 동안 다음 단계 스펙을 쓴다.

## 지킬 것

- **코드는 코덱스가 쓰고 검토는 클로드가 한다.** 위임했다고 검토를 건너뛰지 않는다
- **검증 없이 완료라고 하지 않는다.** 빌드가 안 돌았으면 "미검증"이라고 쓴다
- **미결정을 다음 단계로 넘기지 않는다.** 넘어가기 전에 `AskUserQuestion` 으로 해소한다
- **예고한 범위를 조용히 넓히지 않는다.** 필요하면 멈추고 보고한다
- **다른 도구가 남긴 미커밋 변경을 내 커밋에 섞지 않는다.** 착수 전에 `git status` 로 확인하고,
  내 변경만 경로로 골라 스테이징한다
- **문서와 코드가 어긋나면 즉시 맞춘다.** 결정이 바뀌면 설계 문서도 같은 커밋에서 고친다

## 하지 말 것

- 스펙 없이 "알아서 만들어줘" 로 코덱스 호출하기
- 코덱스 출력만 읽고 `git diff` 확인 없이 다음 단계로 넘어가기
- 보고에 "이제 ~를 하겠습니다"만 쓰고 무엇이 끝났는지 안 적기
- 미결정 사항을 "나중에 정하죠"로 넘기기
- 여러 단계를 한 커밋에 몰아넣기
- 선택지 없이 산문으로 "어떻게 할까요?" 묻기
