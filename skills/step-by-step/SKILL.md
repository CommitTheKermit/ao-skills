# Step by Step

한 번에 한 단계만 진행한다. 각 단계는 독립적으로 검증 가능해야 하며, 다음 단계는 사용자의
승인 전까지 구현하지 않는다.

## 시작 또는 이어받기

1. 적용되는 저장소 지침을 읽는다.
2. `git status`, diff, 최근 커밋과 관련 문서를 확인한다.
3. 인계 내용은 단서로 사용하되, 완료 여부와 현재 코드는 직접 검증한다.
4. 진행 중인 단계, 확정된 결정, 남은 단계를 식별한다.
5. 다른 작업의 변경을 보존하고 현재 단계에 섞지 않는다.

사용자가 구체적인 단계 예고와 함께 `계속`, `ㄱㄱ`처럼 명시적으로 진행을 지시했다면 그 단계를
승인한 것으로 보고 재승인을 묻지 않는다. 작업이나 결과를 바꾸는 결정이 불명확하면 구현 전에
질문하고 기다린다.

## 단계 크기

한 단계는 파일 몇 개부터 한 계층까지로 잡는다. 한 번의 빌드, 테스트 또는 실행으로 옳고 그름을
판별할 수 있어야 한다. 검증 하나로 판단할 수 없다면 더 작게 나눈다.

| 적절 | 과함 |
| --- | --- |
| 값 객체 3개와 테스트 | 도메인 전체 |
| Repository, Fake와 매핑 테스트 | 데이터 계층 전체 |
| 화면 하나의 상태와 UiModel | 화면 여러 개 |

## 반복 절차

`예고 → 승인 → 구현·검토 → 검증 → 보고 → 미결정 해소 → 커밋` 순서로 반복한다.

### 1. 다음 단계 예고

다음을 먼저 제시한다.

- 단계 이름과 번호
- 만들거나 고칠 파일
- 핵심 타입·함수 시그니처와 짧은 코드 스케치
- 따라야 할 기존 규약
- 범위 밖으로 남길 항목
- 이 단계에서 실행할 검증
- 이 단계로 확인될 불확실한 항목

예고만 읽고도 구현 범위를 판단할 수 있을 만큼 구체적으로 쓰되, 아직 코드는 수정하지 않는다.

### 2. 승인

사용자의 승인을 기다린다. 사용자가 파일 하나씩, 단계마다, 큰 덩어리처럼 리듬을 지정하면 작업이
끝날 때까지 유지한다. 승인된 범위 밖의 변경이 필요해지면 조용히 넓히지 말고 멈춰 보고한다.

### 3. 구현과 자체 검토

승인된 파일만 직접 구현한다. 수정할 공용 함수의 모든 호출부와 실제 흐름을 먼저 확인하고, 기존
도우미·표준 기능·설치된 의존성을 우선 재사용한다.

구현 후 실제 diff를 처음부터 끝까지 읽는다. 다음을 확인한다.

- 예고한 요구사항과 일치하는가
- 범위 밖 파일을 건드리지 않았는가
- 기존 사용자 변경을 덮거나 섞지 않았는가
- 불필요한 추상화와 사전 구현이 들어가지 않았는가

### 4. 검증

예고한 빌드, 테스트 또는 실행을 실제로 수행한다. 통과를 추측하지 않는다.

- 실패하면 해당 단계는 끝나지 않은 것이다.
- 승인 범위 안에서 고칠 수 있으면 수정하고 다시 검증한다.
- 범위 확장이 필요하면 멈춰 원인과 필요한 변경을 보고한다.
- 환경 문제로 실행하지 못하면 `미검증`이라고 명시하고 완료로 표현하지 않는다.

### 5. 보고

완료분과 예정분을 구분선으로 분리해 다음 형식을 사용한다. `완료` 위에는 전체 진행 단계를
체크리스트로 표시한다. 끝난 단계는 `[x]`, 다음 단계와 남은 단계는 `[ ]`로 쓰고, 바로 다음
단계에는 `← 다음`을 붙인다. 범위가 합의되어 바뀌면 이 목록도 같이 갱신한다.

```markdown
# 📋 진행 단계

- [x] 1단계: <단계 이름>
- [x] N단계: <방금 완료한 단계 이름>
- [ ] N+1단계: <다음 단계 이름> ← 다음
- [ ] N+2단계: <남은 단계 이름>

---
# ✅ 완료: <단계 이름> (N단계)

## 변경 파일

| 파일 | 내용 |
| --- | --- |
| `경로` | 한 줄 설명 |

## 검증 결과

실행한 명령과 통과 결과. 실행하지 못했다면 `미검증`과 이유.

## 알아낸 것

기존 문서나 예상과 달랐던 사실. 없으면 생략.

## 확인이 필요한 결정

없으면 `없음`.

---
# ⏭️ 다음: <단계 이름> (N+1단계)

## 변경 파일

| 파일 | 내용 |
| --- | --- |

## 핵심

짧은 코드 스케치.

## 함께 검증되는 것

이 단계로 확인할 불확실한 항목.
```

남은 단계가 없으면 진행 단계 체크리스트를 모두 `[x]`로 표시하고, `다음` 대신 전체 완료와 최종
검증 결과를 적는다.

### 6. 미결정 해소

확인이 필요한 결정이 있으면 다음 단계로 넘어가기 전에 질문하고 기다린다. 가능한 경우 구조화된
질문 도구를 사용하고, 없으면 간결하게 직접 묻는다.

- 선택지를 2~3개로 제한한다.
- 추천안을 첫 번째에 두고 `(추천)`을 붙인다.
- 각 선택지에 실제 코드나 화면 형태의 미리보기를 넣는다.
- 선택에 따라 무엇이 달라지고 어떤 손실이 생기는지 숨기지 않는다.
- 답을 받으면 코드와 관련 문서에 함께 반영한다.

### 7. 커밋

단계가 검증되고 미결정이 해소된 뒤 해당 단계의 변경만 커밋한다. 저장소의 브랜치·커밋 규칙과
사용자의 지시를 우선하며, 커밋이 금지되었거나 허용되지 않으면 생략 사실을 보고한다.

커밋 본문에 무엇을 왜 바꿨는지와 단계에서 알아낸 사실을 남긴다. 다른 작업의 미커밋 변경은
스테이징하지 않는다.

## 지킬 것

- 보고마다 전체 진행 단계를 `완료` 위에 표시한다.
- 검증 없이 완료라고 하지 않는다.
- 예고한 범위를 조용히 넓히지 않는다.
- 미결정을 다음 단계로 넘기지 않는다.
- 문서와 코드가 어긋나면 같은 단계에서 맞춘다.
- 다음 단계 승인 전에 다음 단계 코드를 작성하지 않는다.
- 여러 단계를 한 커밋에 섞지 않는다.
