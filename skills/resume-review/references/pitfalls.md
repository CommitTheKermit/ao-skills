# 시행착오

피드백을 실제 이력서에 반영하면서 겪은 실수와 그때 찾은 대응이다. 규칙서가 "무엇을"이라면 이 문서는 "무엇이 꼬이는가"다. 수정 단계에 들어가기 전에 읽는다.

## 누적 편집으로 내용이 사라진다

교육 과정을 경력에서 학력으로 옮기고(1단계), 문장을 줄이고(6단계), 불릿을 빼다 보니 교육 과정의 알맹이가 2쪽 끝 두 줄로 쪼그라들어 있었다. 단계마다 승인을 받았는데도 그랬다. 작성자가 "뭐가 이상하다"고 느끼고서야 발견했다.

- 단계별 diff만 보지 말고 큰 단계가 끝날 때마다 **PDF를 처음부터 끝까지 다시 읽는다.**
- 줄을 옮기거나 지울 때 **빠진 줄 목록**을 보고에 남긴다. 되살릴 때는 기억으로 다시 쓰지 말고 `git show <커밋>:<파일>`의 원문을 가져온다.
- 분류를 바꾸라는 피드백(교육은 경력이 아니다)을 내용을 지우라는 뜻으로 넓히지 않는다.

## 사용자의 수정이 내 커밋에 섞인다

작성자가 파일을 직접 고친 뒤 내가 같은 파일을 고치고 `git add <파일>`을 했더니, 작성자의 변경 세 줄이 내 커밋 메시지 아래 들어갔다. 메시지와 내용이 어긋난 커밋이 생겼다.

- 편집 전에 `git diff -- <파일>`을 본다. 숫자가 아니라 내용을 본다.
- 작성자 변경이 있으면 그 줄은 건드리지 않고, 보고에서 "그대의 수정이 함께 들어갔다"고 밝힌다. 되돌리지 않는다. 서류는 작성자의 것이다.

## 지어낸 숫자를 요구받는다

"기억이 안 나는데 꾸며서라도 넣자", "급하니까 그냥 써"라는 요청이 왔다. 거절하되 빈손으로 끝내지 않았다.

- 저장소에서 진짜 값을 찾는다. 재인코딩 커밋에 남은 영상 파일을 `ffprobe`로 읽어 전후 해상도, 프레임, 크기를 얻었다. 사람의 기억 대신 git 이력의 바이너리가 근거가 된다.
- 측정이 필요하면 측정을 제안한다. 다만 지금 앱과 지금 기기로 잰 값은 과거 개선의 전후가 아니므로, 조건을 밝혀 따로 적는 데만 쓴다.
- 작성자가 본인 기억의 숫자를 넣기로 하면 넣되, 근거 문서에 "본인 기억, 기록 없음"과 예전 메모와의 불일치를 적는다. 내가 거짓임을 아는 값(앱이 꺼진 채 잰 온도)은 적지 않고, 작성자가 직접 고칠 수 있는 위치와 명령을 알려 준다.

## 공개 저장소 링크의 함정

이력서에 적은 저장소의 기능이 작업 브랜치에만 있고 기본 브랜치에는 없었다. 측정 문서는 비공개 저장소에 있었다. 심사자는 둘 다 볼 수 없다.

- 링크를 적을 때 `gh api repos/<owner>/<repo>/contents/<경로>?ref=main`으로 기본 브랜치에 그 파일이 있는지 본다.
- 병합이 필요하면 공개 전 점검(비밀값, 개인 절대경로, 내부 주소)을 거친다. 이 점검은 별도 세션으로 떼어 내는 편이 안전하다.
- 저장소의 스킬 수나 커밋 수는 브랜치마다 달라 이력서에 쓰지 않는다. 쓰려면 기본 브랜치 기준으로 다시 센다.

## 포트폴리오가 이력서와 다른 말을 한다

이력서에서 프로젝트 하나를 뺐는데 공개 포트폴리오에는 그대로 있고, 새로 넣은 프로젝트는 포트폴리오에 없었다. 틀린 내용은 아니지만 제출 전에 작성자가 알아야 한다. 포트폴리오 갱신은 외부 공개라 작성자가 정한다.

## 기호 일괄 치환

가운뎃점을 쉼표로 전부 바꾸라는 요청에 치환을 돌렸더니 "5974×1080·60fps·5.5MB"가 쉼표 나열이 되어 더 읽기 어려워졌다. 치환 전에 수치 나열 문장을 따로 골라 띄어쓰기로 풀었다. 치환 뒤에는 반드시 화면으로 본다.

## 고정 높이 레이아웃의 넘침

HTML을 A4로 뽑는 이력서는 `.page`가 고정 높이라 넘친 내용이 다음 쪽으로 가지 않고 **잘린다.** 처음에는 머리글이 겹쳐 보였는데, flex 컨테이너가 자식을 찌그러뜨린 탓이었다. `.page > * { flex: none; }`을 넣어야 넘침이 숫자로 드러난다.

### 쪽 넘침 측정

헤드리스 브라우저로 쪽마다 `scrollHeight/clientHeight`와 마지막 자식의 아래 여백을 찍는다.

```sh
sed 's#</body>#<script>document.fonts.ready.then(()=>{const r=[...document.querySelectorAll(".page")].map(p=>p.scrollHeight+"/"+p.clientHeight+" 여백 "+(p.clientHeight-Math.round(p.lastElementChild.getBoundingClientRect().bottom-p.getBoundingClientRect().top)));const e=document.createElement("pre");e.id="measure";e.textContent=r.join(" , ");document.body.append(e)})</script></body>#' resume.html > .measure.html
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu --virtual-time-budget=15000 --dump-dom "file://$PWD/.measure.html" | grep -o '<pre id="measure">[^<]*'
rm -f .measure.html
```

`scrollHeight`가 `clientHeight`보다 크면 잘린 것이다. 여백이 음수면 마지막 항목이 쪽 밖에 있다.

## 쪽 균형

1쪽과 2쪽의 내용량이 달라 같은 간격으로는 한쪽만 빈다. 쪽별로 항목 간격을 다르게 주고(`.page:not(.first) { gap: 32px }`), 줄 간격을 넓힐 때는 불릿 표시의 세로 위치도 같이 옮긴다. 내용을 억지로 한 쪽에 몰아넣으면 첫 쪽이 빽빽해져 가독성이 먼저 나빠진다.

## 시안 비교

- 문구 원본 HTML 하나에 CSS만 갈아 끼워 시안을 만들면, 뒤에 문구를 고쳐도 시안을 다시 뽑을 수 있다. 문구 동일 여부는 태그를 벗기고 글자만 비교한다.
- 2열을 1열로 바꾼 시안을 먼저 보여 줬다가 "원래 구조를 유지해 달라"는 말을 들었다. 구조 변경은 작성자에게 먼저 묻고, 유지 시안과 함께 낸다.
- 색만 비교할 때는 전체 쪽 대신 같은 영역을 잘라 한 장에 여섯 개를 놓는다. 띠 위 흰 글자와 라벨 박스 위 글자의 명도 대비를 숫자로 적어 두면 인쇄 걱정에 답할 수 있다.

## 링크 검사

`curl`로 열면 자동화 차단으로 403이 나오는 페이지가 브라우저에서는 정상이었다. 403이 나오면 브라우저로 다시 열고, 서비스 페이지는 실제 내용까지 읽어 운영 중인지 본다. 리뷰어는 정말로 스토어에 들어가 본다.

## 숫자와 문구 대조

문장을 줄일 때 숫자가 조용히 빠질 수 있다. 전후 텍스트의 숫자를 다중집합으로 비교하면 "4명 팀"의 4처럼 사라진 숫자가 바로 드러난다. 링크 글자를 바꿀 때는 `href` 목록이 같은지 비교한다. 번들 스크립트 `scripts/compare_text.py`가 이 둘과 금지 기호를 한 번에 본다.

## 정직성은 정책이 아니라 판단이다

"왜 안 넣어 주느냐, 정책이냐 메모리냐"는 질문을 받았다. 답은 둘 다 아니다. 틀린 줄 아는 사실을 채용 서류에 적으면 그 서류를 읽는 회사를 속이는 데 가담하게 된다. 작성자를 못 믿어서가 아니라, 내가 거짓임을 아는 경우에만 멈춘다. 그래서 기억에 근거한 값은 넣고(근거 수준을 적고), 조건이 다른 측정값은 넣지 않았다. 작성자가 직접 고치는 것까지 막지는 않는다.

## 면접용 재료를 버리지 않는다

이력서에서 뺀 숫자(클릭 수, 유입 경로, 일치도)와 사건(코드 리뷰, SDK 연동)은 근거 문서에 "면접용"으로 모아 둔다. 서류에는 결론 하나만 두고 꼬리 질문이 오면 꺼낸다. 수치마다 근거 수준(저장소 확인, 측정 기록, 본인 기억)을 함께 적는다.
