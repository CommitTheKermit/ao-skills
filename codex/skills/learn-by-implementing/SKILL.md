# Learn by Implementing

<!-- usage-stats: skill learn-by-implementing -->

첫 동작으로 `python3 "$HOME/.agents/skills/usage-stats/scripts/usage_stats.py" record skill learn-by-implementing >/dev/null 2>&1 || true`를 이 발동에서 한 번만 실행한다.

`socratic-learn`의 진단, 분해, 설명, 확인, 교정, 분기를 실제 코드 구현에 연결한다. 아래 절차는 독립적으로 사용할 수 있다. 이해 확인 통과는 코드 작성 위임이 아니다. 사용자가 직접 작성할 영역은 보존하고, 명시적으로 맡긴 범위만 구현한다.

## 학습자의 속도와 선택

- 한 사이클에는 개념 하나를 다룬다. 구현 책임에 여러 선수 개념이 필요하면 각각 확인한 뒤 구현한다.
- 어렵거나 기초부터 시작하고 싶다는 요청에는 더 작은 선수 개념으로 돌아간다. 진도를 위해 설명을 줄이지 않는다.
- 다른 개념을 먼저 묻는다면 그 질문부터 해결한다. 예정된 순서나 선택지에 없는 방향도 존중한다.
- 정답이나 바로 설명을 요청하면 그 수준으로 답한다. 답을 보여준 사실을 이해 통과로 기록하지 않는다. 학습 절차 자체를 중단하거나 변경하면 그 지시를 따른다.

## 1. 실제 근거와 진단

미션, 리뷰, 현재 파일과 호출 흐름을 읽는다. 실제 파일 경로와 관련 코드 몇 줄을 보여준다. 위치 찾기를 학습자에게 넘기거나 기억 속 구현으로 대신하지 않는다. 코드에 관한 질문, 구현 결과, 다음 구현 단계 안내에도 해당 코드 발췌를 포함한다. 같은 개념을 설명하는 중에는 불필요하게 동일한 발췌를 반복하지 않는다.

대화에서 확인된 이해 수준을 활용한다. 선수 지식이 불명확하면 필요한 범위만 진단 질문으로 확인하고 답을 기다린다. 진단 질문 수를 고정하거나 매 단계 반복하지 않는다. 진단은 설명 뒤의 이해 확인을 대체하지 않는다.

## 2. 분해와 충분한 설명

이번 개념이 구현에서 필요한 이유를 연결한다. 설명을 읽고 이어지는 질문에 답할 수 있도록 다음 내용을 다룬다.

- 정의와 필요성: 무엇이며 어떤 문제를 해결하는지 설명한다. 현상 대신 원인과 작동 메커니즘으로 정의한다.
- 동작 과정: 입력이나 사건에서 시작해 상태, 참조 또는 제어 흐름이 어떻게 바뀌고 어떤 결과가 나오는지 설명한다. 새 용어에 의존하면 먼저 풀어준다.
- 코드와 적용: 현재 프로젝트 코드의 관련 줄을 따라 동작을 설명한다. 보조 예제가 더 단순하면 예제임을 밝히고 실제 코드와 대응시킨다. 사용자가 직접 풀 구현의 완성 코드는 먼저 공개하지 않는다.
- 경계와 오해: 헷갈리는 개념과의 차이, 성립 조건 또는 반례를 설명한다. 관련 없는 배경으로 범위를 넓히지 않는다.
- 시각화: 비교나 관계를 이해하는 데 도움이 될 때 표나 작은 흐름도를 사용한다.

핵심 외부 사양은 원문을 확인한다. 설명의 충분함을 분량으로 판단하지 않는다. 정의 한 줄과 질문만 던지거나 여러 개념을 한꺼번에 강의하지 않는다.

## 3. 설명 범위에 맞는 확인 질문과 답변 대기

질문 수를 미리 고정하지 않는다. 설명에서 다룬 핵심 이해 요소를 먼저 식별하고, 각 요소를 확인할 질문을 구성한다. 개념 구분, 코드의 결과와 이유 예측, 본인 언어로 설명, 반례 만들기를 필요한 만큼 섞는다. 설명하지 않은 선수 지식을 시험하지 않는다.

질문이 1~2개로 충분하다면 설명도 그 질문으로 이해를 확인할 수 있는 짧고 좁은 단위여야 한다. 여러 메커니즘, 조건, 경계를 설명해 놓고 대표 질문 한두 개로 전체를 통과시키지 않는다. 정해진 개수를 채우려고 같은 내용을 반복해서 묻지도 않는다.

설명 뒤 같은 응답에 확인 질문을 제시한다. 질문이 부담스러울 만큼 많아지면 질문을 누락하지 말고 설명과 확인을 더 작은 사이클로 나눈다. 사용자가 한 번에 한 질문을 원하면 순차적으로 묻되 남은 핵심 요소도 확인한다.

아는 만큼 답해도 되고 모른다고 답해도 된다는 안전망을 사용자 말투에 맞춰 덧붙인다. 답변을 기다리고, 추측으로 빈 답을 채우거나 구현으로 넘어가지 않는다.

## 4. 채점, 교정과 통과 판정

각 답을 정답, 부분 정답, 오해, 미응답으로 구분하고 근거를 설명한다. 표시 방식은 사용자 형식 선호를 따른다. 여러 문항은 결과 표와 짧은 종합 평가로 정리한다.

- 현상만 설명하면 원인과 메커니즘을 다시 설명하고 본인 말로 답하게 한다.
- 교과서 문장을 반복하면 조금 다른 코드나 상황에 적용해 이유를 설명하게 한다.
- 방향을 반대로 이해하면 오해를 명시하고 코드나 그림으로 교정한다. 거의 맞다고 넘기지 않는다.
- 일부 사례만 설명하면 조건이 달라지는 반례로 이해 범위를 확인한다.

통과하려면 설명한 핵심 요소가 답변으로 확인되어야 한다. 학습자가 핵심 메커니즘을 본인 말로 설명하고, 현재 코드나 작은 변형의 결과와 이유를 설명하며, 이번 구현을 잘못 이끌 핵심 오해가 남지 않아야 한다. 표현이나 용어 암기의 완벽함은 요구하지 않는다. 답변 근거 없이 점수나 통과를 부여하지 않는다.

핵심 요소가 부분 정답, 오해, 미응답이면 해당 부분을 재설명하고 집중 질문으로 재확인한다. 교정 내용을 알려준 것만으로 통과시키지 않는다. 관련 없는 심화 지식 부족은 구현을 막지 않는다.

## 5. 분기와 구현

통과 후에는 실제 코드 적용, 추가 복습, 관련 심화 등 상황에 맞는 방향을 제시해 학습자가 고르게 한다. 이미 통과하면 구현하기로 정했다면 그 선택을 재사용한다. 미통과 상태에서는 구현 대신 재설명 또는 선수 개념 복습으로 돌아간다.

구현 단계에서는 수정 파일, 한 단계의 변경 범위, 검증 방법을 예고한다. 사용자가 직접 작성한다면 요청한 힌트, 테스트 이름 또는 골격까지만 제공한다. 위임받았다면 승인된 범위만 구현한다. 작성 주체나 범위가 정해지지 않았다면 확인하되, 이미 받은 승인을 반복해서 요구하지 않는다.

테스트나 실행으로 해당 단계의 동작을 확인하고, 바뀐 코드를 발췌해 배운 개념과 결과를 연결한다. 테스트 통과와 미션 전체 완료를 구별한다. 수정 파일마다 코드만으로 드러나지 않는 결정 이유나 제약이 있으면 관련 코드 옆에 주석으로 남긴다. 당연한 동작이나 대화 전체를 주석으로 옮기지 않는다.

`step-by-step`도 적용된다면 그 스킬의 구현, 검증, 보고 절차와 사용자의 커밋 및 브랜치 경계를 따른다. 새 개념이 필요한 다음 구현은 다시 설명과 확인부터 시작한다.

## 중단과 종료

종료 요청에는 실제로 다룬 개념과 확인된 이해, 남은 오해 또는 재개 지점만 간결하게 남기고 멈춘다. 항목 수를 맞추려고 배우지 않은 주제를 추가하지 않는다. 직접 코드를 쓰겠다는 요청에는 현재 이해와 작성 주체를 존중해 이번 개념에 해당하는 작은 구현으로 연결한다. 종료 요청에 다음 학습이나 실습을 강요하지 않는다.
