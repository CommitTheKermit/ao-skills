# Flow First

<!-- usage-stats: skill flow-first -->

첫 동작으로 `python3 "$HOME/.agents/skills/usage-stats/scripts/usage_stats.py" record skill flow-first >/dev/null 2>&1 || true`를 이 발동에서 한 번만 실행한다.

사용자가 기대하는 행동과 결과를 코드 작성 전에 맞추고, 같은 기준으로 완료를 판단한다.
기능의 의미와 화면 사이 상태 변화를 먼저 확인한다. 파일 구조나 구현 방법까지 매번 승인받지 않는다.

## 1. 기존 근거와 실제 흐름 확인

- 해결하려는 문제와 작업 범위를 짧게 재진술한다. UI 결정이 있으면 구현하려는 화면과 상호작용도 먼저 알린다.
- 적용되는 저장소 지침과 추적 중인 변경을 확인한다. 이번 기능의 이슈, 디자인, 동작 명세, API 계약, 호출부와 테스트만 읽는다.
- 이미 구현된 기능은 진입점에서 인증, 입력, 저장, 화면 이동, 재조회까지 추적한다. 공용 함수를 바꾸기 전에는 모든 호출부를 확인한다.
- 자료별 역할을 구분한다. 디자인의 시각적 배치와 명시된 동작, 제품 정책, API의 요청과 응답, 코드의 현재 동작을 대조한다. 문서 이름만으로 우선순위를 정하거나 디자인에 책 3권이 보인다는 이유로 선택 기준과 저장 위치를 추정하지 않는다.
- 불일치가 있으면 `근거 A / 근거 B / 달라지는 사용자 동작`을 출처와 함께 제시한다. 최신 사용자 결정으로 해결되는 충돌은 그 결정을 적용하고 낡은 문서를 표시한다. 나머지는 구현 전에 묻는다.
- 읽지 못한 원본은 미확인으로 남긴다. 수정 가능한 이슈 본문이나 PR 제목만으로 당시 합의와 AI 오해를 단정하지 않는다.

## 2. 사용자 동작 합의

기존 명세나 현재 대화에 아래 내용을 간결하게 정리한다. 별도 대형 기획서나 새 문서 체계를 만들지 않는다.

```markdown
목적: 사용자가 해결하려는 문제
기준: 문서·이슈·디자인·API 경로와 적용한 사용자 결정
기존 동작에서 바뀌는 점:
정상 흐름: 시작 상태 → 행동 → 필요한 인증·입력 → 저장 성공 → 결과 확인 → 종료 또는 원래 화면 복귀

| 조건·행동 | 기대 화면·결과 | 데이터·상태 변화 |
| --- | --- | --- |
| 정상 완료 | 확인할 결과와 이동 위치 | 저장값, 갱신할 다른 화면 |
| 관련 취소·실패·재진입 | 유지할 화면과 재시도 위치 | 유지·폐기할 입력과 보류 작업 |

미정·충돌: 결과가 달라지는 결정만
범위 밖: 이번 작업에서 다루지 않는 동작
검증: 각 기대 결과를 확인할 테스트 또는 실제 조작
```

- 기능의 의미가 갈리면 서로 다른 결과가 나오는 구체적인 예시로 질문한다. 예: 별점 창의 책 목록은 최근 평가 순서인지, 현재 선택 점수와 비교할 책인지.
- 위 틀에서 해당하는 단계만 남긴다. 조회 기능에 저장을 넣거나 복귀가 없는 흐름에 새 이동을 만들지 않는다.
- 이번 흐름에 해당하는 경계만 포함한다. 인증 성공 후 원래 행동 재개, 취소 후 보류 작업 제거, 저장 실패 시 입력 유지, 다른 화면 갱신, 뒤로 가기와 재실행 시 복원 등이 후보이며 전부를 기계적으로 추가하지 않는다.
- 아직 합의하지 않은 사용자 동작은 초안을 먼저 보여주고 확인을 기다린다. 답이 없다고 승인으로 간주하지 않는다. 그동안 의존하지 않는 코드·자료 조사는 계속할 수 있다.
- 이미 같은 동작을 사용자가 명시하거나 확인했다면 재승인을 요구하지 않는다. 구현 상세는 기존 패턴으로 판단한다.
- 정책이 바뀌면 변경 전후, 영향받는 흐름과 검증을 갱신한다. 사용자가 명시한 변경은 그대로 반영하고, 새 미정 사항만 묻는다.

## 3. 작은 왕복 흐름 구현

- 한 조각은 화면 하나나 계층 하나가 아니라 사용자가 결과를 확인할 수 있는 흐름으로 잡는다. 예: 검색 → 상세에서 저장 → 서재 반영 확인 → 검색 복귀.
- 합의된 범위에서는 조각마다 별도 승인을 반복하지 않고 구현과 검증을 이어간다. 사용자가 단계별 승인을 요청한 경우에는 그 리듬을 따른다.
- 기존 코드, 표준 기능, 설치된 의존성을 재사용한다. 이 스킬을 이유로 상태 머신 프레임워크나 대규모 리팩터링을 추가하지 않는다.
- ID 조회처럼 보이는 함수 안에 저장을 숨기지 않는다. 자동 등록 후 별점 저장처럼 쓰기가 연속되면 순서와 부분 성공 시 표시할 결과를 명시한다.
- 같은 화면, 인증, 저장 경로를 고치는 다른 작업이 있으면 변경 순서와 통합 기준을 확인한다. 단독 브랜치의 성공을 합쳐진 앱의 성공으로 취급하지 않는다. 무관한 변경을 임의로 병합하지 않는다.
- 객체지향 책임 위반을 발견하면 실제 영향과 코드 근거를 제시한다. 구조 변경은 이번 흐름을 바로잡는 데 필요한 범위로 제한한다.

## 4. 합의한 결과로 검증

- 테스트 기대값은 2단계에서 합의한 예시에서 가져온다. 구현 결과에 맞춰 기대값이나 명세를 몰래 바꾸지 않는다.
- 동작을 구분하는 최소 회귀 테스트를 기존 테스트 체계에 추가하거나 보강한다. 저장·복원, 요청 순서, 목록 연속 로딩처럼 깨졌을 때 실패하는 검증을 우선한다. 단순 문구나 스타일 수정에 테스트를 억지로 추가하지 않는다.
- UI 흐름은 실제 앱에서 왕복 조작하고 중요한 상태 경계를 확인한다. 화면이 열리는 스크린샷이나 빌드 통과만으로 인증 후 재개, 저장 반영, 취소 처리를 검증했다고 하지 않는다.
- 테스트 계정과 데이터를 우선 사용한다. 계정 삭제 등 실제 사용자 데이터를 훼손할 조작은 검증 명목으로 실행하지 않는다. 수행하지 못한 경로는 이유와 함께 미검증으로 남긴다.
- 검증한 브랜치·커밋 또는 작업 상태, 앱 산출물·기기 중 필요한 식별자를 기록한다. 통합이나 후속 변경이 있었다면 영향받는 흐름을 해당 결과물에서 다시 확인한다.

## 5. 근거와 완료 상태 정리

- 실제 변경한 정책은 기존 동작 명세에도 반영한다. 이슈·PR이 낡았다면 허용된 범위에서 갱신하고, 권한이 없으면 수정 초안을 준비해 미반영 사실을 알린다.
- 이 스킬은 외부 쓰기나 메시지 전송을 추가 승인하지 않는다. 이슈·PR 생성, 게시, 병합과 push는 사용자 지시와 저장소 규칙을 따른다.
- 짧게 보고한다: `합의한 동작 / 구현 결과 / 실행한 검증과 근거 / 미검증·문서 미반영`.
- 필수 흐름이나 필요한 문서 갱신이 남아 있으면 전체 완료로 표현하지 않는다. 실패가 있으면 영향받는 합의 항목으로 돌아가 수정한다.
- 커밋은 저장소 규칙에 따라 작업 결과만 포함한다. 최종 PR 본문은 초기 계획이 아닌 실제 동작과 검증 상태를 설명한다.
