# GitHub PR Review

<!-- usage-stats: skill github-pr-review -->

첫 동작으로 `python3 "$HOME/.agents/skills/usage-stats/scripts/usage_stats.py" record skill github-pr-review >/dev/null 2>&1 || true`를 이 발동에서 한 번만 실행한다.

특정 PR 리뷰 요청은 확인된 문제를 그 PR에 인라인 코멘트로 제출해 달라는 요청으로 처리한다. 코드, 브랜치, PR 본문은 수정하지 않는다.

GitHub에 게시하는 리뷰 본문, 인라인 코멘트와 리뷰 요약은 다른 개발자가 읽는 공유 산출물이다. 대화에서 사용하는 캐릭터 말투나 영애체를 적용하지 않고, 간결하고 중립적인 한국어 협업 문체로 작성한다. 이 문체 제한은 사용자와의 채팅 응답에는 적용하지 않는다.

## 절차

1. 저장소의 `AGENTS.md`와 하위 작업 규칙을 읽는다.
2. URL이나 번호가 있으면 해당 PR을 사용한다. 없으면 현재 브랜치에 연결된 PR을 `gh pr view`로 찾는다. 대상이 하나로 정해지지 않으면 사용자에게 묻는다.
3. base와 head SHA를 기록하고 전체 diff를 읽는다. 아래 검토 범위 절차로 변경 함수의 실제 호출자, 관련 상태와 테스트를 추적한다. 이전 리뷰와 비교할 때는 먼저 SHA 차이를 확인한다.
4. 필요한 최소 검증을 실행하고 아래 반증 절차로 각 발견 사항의 도달 가능성, 재현 조건과 영향을 확인한다.
5. 다음 항목만 finding으로 남긴다.
   - 동작 오류, 회귀, 데이터 손실, 보안 또는 접근성 문제
   - 테스트가 잘못 통과하거나 중요한 경로를 검증하지 못하는 문제
   - 구체적인 유지보수 실패를 만드는 객체지향 법칙 위반
6. 취향, 단순 스타일, 근거 없는 가능성, 칭찬은 코멘트하지 않는다. 기존 리뷰 코멘트와 중복되지 않는지 먼저 확인한다.
7. finding은 실제 변경된 오른쪽 줄에 인라인 코멘트로 연결한다. 일반 PR 코멘트로 대체하지 않는다. 코멘트에는 관찰된 영향, 발생 이유, 최소 수정 방향을 짧게 쓴다. 관련 없는 줄에 억지로 연결하지 않는다.
8. finding이 있으면 GitHub CLI로 하나의 `COMMENT` 리뷰에 인라인 코멘트를 묶어 제출한다. 리뷰 본문과 각 코멘트는 중립적인 한국어 협업 문체로 작성한다. `APPROVE`나 `REQUEST_CHANGES`는 사용자가 별도로 요청한 경우에만 사용한다.
9. finding이 없으면 빈 리뷰나 일반 코멘트를 만들지 않고, 검사 범위와 발견 사항 없음만 보고한다.

## 검토 범위와 병렬 분담

- 변경 규모에 맞는 작업 메모에 `변경 대상 -> 실제 호출자/진입점 -> 영향받는 상태나 계약 -> 검증 근거 또는 미검증 사유`를 기록한다. 파일을 읽었다는 기록만으로 동작을 검증했다고 표시하지 않는다.
- 공통 컴포넌트와 API 변경은 변경되지 않은 호출자도 검색하고 호환성을 확인한다. 선언, import, 테스트 전용 호출과 실제 앱 진입 경로를 구별한다. 문자열 검색에 호출자가 없더라도 라우팅 등록, 리플렉션, 외부 공개 API 사용 가능성이 있으면 해당 연결을 추가 확인한다.
- 상태를 소비하는 화면은 해당 변경에 관련된 로딩, 성공, 빈 결과, 실패와 재시도 경로를 대조한다. 서로 다른 상태를 기본값이나 빈 목록으로 합치는 코드는 그 결과 사용자가 보는 화면과 가능한 행동까지 확인한다.
- 병렬 리뷰가 요청되면 PR별 담당뿐 아니라 변경 위험에 따른 관점도 배정한다. 예를 들어 공통 컴포넌트 호출자 호환성, 실패와 복구 경로, 환경 설정 전달을 분담하고 PR 사이의 의존 경계도 확인한다. 작은 변경에 불필요한 담당이나 전수 조합을 만들지 않는다.
- finding 개수로 검토를 종료하지 않는다. 정한 범위를 확인하거나 미검증 사유를 기록한 뒤 종료한다. 같은 전체 리뷰를 새 근거 없이 반복하지 않고 남은 검증 공백을 대상으로 확인한다.

## 검증과 finding 반증

- 테스트 통과 수보다 의심한 경로가 실제 실행됐는지 확인한다. 컴파일이나 모델 단위 테스트를 UI 진입, 레이아웃 측정, 클릭 동작의 실행 증거로 사용하지 않는다. 검증은 위험에 맞는 최소 실행으로 제한한다.
- 후보마다 실제 진입점부터 문제 줄까지의 연결, 이번 diff로 생긴 변화, 기존 방어 코드, 발생 조건과 사용자 영향을 확인한다. 호출되지 않는 선언의 문제를 현재 사용자 경로의 장애로 단정하지 않는다.
- 최종 검증자는 후보가 틀릴 수 있는 이유를 먼저 찾는다. 병렬 리뷰에서는 다른 담당이나 통합 담당이 핵심 코드와 실행 결과를 직접 확인한다. 위임 결과의 파일 경로와 심각도만 옮기지 않는다.
- 직접 재현한 결과와 코드 추론을 구분한다. 정적으로 확정 가능한 문제는 호출 경로와 필수 조건을 근거로 남길 수 있지만, 실행하지 않은 크래시를 재현했다고 표현하지 않는다. 도달 가능성이나 핵심 조건이 미확인이면 확정 finding에서 제외하고 필요한 검증을 보고한다.
- 심각도는 확인된 영향과 발생 조건으로 결정한다. 크래시 가능성이라는 표현만으로 P1을 부여하지 않는다. 실제 객체지향 법칙과 구체적인 실패를 설명할 수 없으면 단순 책임 중복을 법칙 위반으로 포장하지 않는다.
- 게시 직전에 PR head가 검토 SHA와 같은지 확인한다. 달라졌으면 영향을 받는 경로와 인라인 줄을 다시 검증한다.

마지막에는 리뷰 URL, 인라인 finding 수, 핵심 발견 사항, 실행한 검증과 확인하지 못한 범위를 보고한다. 발견 사항 없음은 검토 범위 안의 결론이며 결함 부재의 보장이 아니다.
