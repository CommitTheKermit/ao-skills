# Sol 두 차례 독립 PR 리뷰와 수정

<!-- usage-stats: skill sol-two-pass-pr-review -->

첫 동작으로 `python3 "$HOME/.agents/skills/usage-stats/scripts/usage_stats.py" record skill sol-two-pass-pr-review >/dev/null 2>&1 || true`를 이 발동에서 한 번만 실행한다.

1차 독립 리뷰 2건 -> 확인된 문제 수정 -> 새로운 리뷰어의 2차 독립 리뷰 2건 -> 확인된 문제 수정 순서로 진행한다. 정상 완료 기준은 총 4명의 독립 리뷰와 두 차수의 수정 결과 보고다. 1차 발견 사항이 없어도 2차를 수행한다.

## 범위와 기준

- 저장소와 하위 `AGENTS.md`를 읽고 요구사항을 짧게 재진술한다. PR은 URL, 번호 또는 현재 브랜치의 PR로 확정한다. 결과를 바꾸는 요구사항이나 대상이 불명확하면 먼저 질문한다.
- 대상 작업의 기존 브랜치와 전용 워크트리를 재사용한다. 수정 전 `git status --untracked-files=no`로 기존 변경을 확인하고, 다른 작업의 변경과 섞지 않는다.
- 이 워크플로 실행 요청은 해당 PR의 리뷰, 확인된 문제 수정, 관련 검증과 인라인 리뷰 게시를 포함한다. 새 이슈나 PR 생성, 병합, 배포, 강제 푸시, `APPROVE`, `REQUEST_CHANGES`는 포함하지 않는다. 저장소별 승인 규칙도 적용한다.
- GitHub 조회와 게시에는 `gh` CLI를 사용한다. 코드 수정, 리뷰 게시와 커밋은 주 에이전트만 담당한다.

## 호출 경로 검토와 후보 반증

- 전체 diff를 읽고 `변경 대상 -> 실제 호출자/진입점 -> 영향받는 상태나 계약 -> 검증 근거 또는 미검증 사유`를 추적한다. 공통 컴포넌트와 API는 변경되지 않은 호출자의 호환성도 확인한다. 선언, import, 테스트 전용 호출을 실제 앱 진입 경로와 구별한다.
- 영향을 받는 화면의 로딩, 성공, 빈 결과, 실패와 재시도 경로를 대조한다. 서로 다른 상태를 기본값이나 빈 목록으로 합치면 사용자가 보는 화면과 가능한 행동까지 확인한다.
- 후보마다 이번 diff로 생긴 변화, 실제 도달 가능성, 기존 방어 코드, 발생 조건과 사용자 영향을 확인한다. 후보가 틀릴 수 있는 이유를 먼저 찾는다. 객체지향 법칙 위반은 구체적인 유지보수 실패와 연결될 때만 finding으로 남긴다.
- finding은 근거가 확인된 동작 오류, 회귀, 데이터 손실, 보안, 접근성, 테스트의 잘못된 통과 또는 중요한 경로를 검증하지 못하는 문제로 제한한다. 취향, 단순 스타일, 칭찬과 근거 없는 가능성은 제외한다.
- 직접 재현한 결과와 코드 추론을 구분한다. 정적으로 확정 가능한 문제는 호출 경로와 필수 조건으로 설명할 수 있다. 도달 가능성이나 핵심 조건이 미확인이면 확정 finding에서 제외하고 검증 공백으로 보고한다. 심각도는 확인된 영향과 발생 조건으로 결정한다.
- 테스트 수보다 문제 경로가 실제 실행됐는지 확인한다. 컴파일이나 모델 단위 테스트를 UI 진입, 레이아웃 측정 또는 클릭 동작의 실행 증거로 대신하지 않는다. finding 개수가 아니라 정한 범위의 검토와 검증 공백 기록을 기준으로 종료한다.
- stacked PR은 선언된 선행 PR을 비교 기준으로 삼는다. 사용자가 코드나 리뷰 갱신을 알리거나 기준 SHA가 바뀌면 영향을 받는 결론과 위임 입력을 갱신한다.

## 리뷰어 생성과 독립성

각 차수에 `collaboration.spawn_agent`로 새 리뷰어 2명을 생성한다. 다음 값을 정확히 지정한다.

```text
model: gpt-6.1-sol
reasoning_effort: high
fork_turns: none
task_name: sol_r1_a / sol_r1_b / sol_r2_a / sol_r2_b
```

- `create_thread`로 사용자 소유 채팅을 만들지 않는다. 이전 차수 리뷰어를 재사용하거나 기존 대화를 상속하지 않는다.
- 두 리뷰어 모두 같은 base/head SHA의 전체 PR diff와 실제 호출 경로를 독립적으로 검토한다. 추가 집중 관점을 줄 수 있지만 전체 검토 범위를 서로 나눠 생략하지 않는다.
- 다른 리뷰어의 발견 사항, 주 에이전트의 의심과 결론, 이전 대화는 전달하지 않는다. 2차 리뷰어에게도 1차 발견 사항이나 수정 설명을 전달하지 않는다. 기존 리뷰 코멘트와 수정 커밋 메시지를 답안으로 사용하지 않도록 한다. 변경된 코드와 원래 요구사항은 제공한다.
- 리뷰어는 소스와 GitHub를 읽고 근거를 수집한다. 파일 수정, 커밋, 리뷰 게시, 설치와 배포는 맡기지 않는다. 테스트가 필요하면 주 에이전트에게 명령과 이유를 제안하도록 해 공유 빌드 경합을 피한다.
- 지정 모델, high 설정 또는 독립 세션을 사용할 수 없으면 임의로 대체하지 않는다. 실행 가능한 작업의 결과와 미완료 리뷰를 보고하고, 두 차수 완료로 표시하지 않는다.

리뷰어 입력에는 아래 정보를 제공한다.

```text
대상 PR URL, 저장소와 워크트리 경로, 정확한 base SHA와 head SHA
원래 요구사항과 확인된 API/동작 계약
변경 파일 목록, 선행 PR 의존성과 비교 기준
검토 기준: 이 스킬의 '호출 경로 검토와 후보 반증' 절
반환 형식: 후보별 심각도, 파일/줄, 발생 조건, 실제 호출 경로,
           이번 diff로 생긴 영향, 반증한 방어 코드, 근거와 미검증 범위
제약: 읽기 전용, 다른 리뷰와 이전 결론 열람 금지, 발견 건수 할당 없음
```

## 차수별 실행

### 1. 기준 고정과 독립 리뷰

1. PR의 base/head SHA, Draft/병합 상태, 의존 관계, 미해결 리뷰와 CI를 조회한다. 주 에이전트가 기존 코멘트의 중복 여부를 관리하고 리뷰어에게 이전 결론을 넘기지 않는다.
2. 워크트리의 검토 대상이 해당 head와 일치하고 다른 변경이 없는지 확인한다. 차수와 검토 SHA를 기록한 뒤 새 리뷰어 2명을 시작한다.
3. 두 결과를 모두 받은 뒤 후보별 핵심 코드와 근거를 직접 재확인한다. 중복은 합치고, 도달 불가능하거나 기존 문제인 후보, 취향과 추측은 제외한다. 구체적인 객체지향 법칙 위반은 법칙과 실제 실패 조건을 함께 제시한다.
4. 검토 중 외부 변경으로 head나 작업 파일이 바뀌면 영향을 받는 결론을 그대로 사용하지 않는다. 새 기준으로 필요한 재검토를 마친 경우에만 유효한 리뷰로 계산하고, 완료하지 못했다면 해당 차수를 미완료로 보고한다.

### 2. 인라인 리뷰 기록

확인된 수정점이 있으면 **수정 전에** 검토한 SHA의 실제 변경 줄에 인라인 코멘트를 남긴다.

- 게시 직전 PR head와 줄을 다시 확인한다. 실제 변경된 오른쪽 줄에 연결하고 `COMMENT` 리뷰 한 건에 해당 차수의 코멘트를 묶는다.
- 각 코멘트는 `[P1]` 등 심각도와 구체적인 문제 제목, 발생 조건과 영향, 원인과 최소 수정 방향을 중립적인 한국어로 담는다. 차수도 표시해 수정 결과와 연결한다.
- 관련 없는 변경 줄에 억지로 연결하거나 일반 PR 코멘트로 대체하지 않는다. 변경 줄에 연결할 수 없는 메타데이터 실패와 범위 밖 문제는 결과 보고에서 구분한다.
- 기존 스레드와 같은 문제가 다시 확인되면 재발로 기록하고 기존 인라인 스레드에 근거를 보강한다. 별개의 문제는 새 인라인 코멘트로 남긴다.
- 발견 사항이 없으면 빈 리뷰를 게시하지 않는다. 게시 실패는 별도 미완료 항목으로 기록하며, 허용된 수정과 검증은 계속할 수 있다. 게시되지 않은 리뷰를 완료했다고 표현하지 않는다.

### 3. 수정과 검증

1. 확인된 문제만 대상 작업 범위에서 수정한다. 요구사항을 바꾸는 해법 선택이 필요하면 먼저 질문한다.
2. 문제 경로에 필요한 검증을 실행하고 결과를 기록한다. 공통 코드의 테스트 통과를 Android/iOS 실행 증거로 대신하지 않는 등 플랫폼별 검증 규칙을 적용한다.
3. 저장소 규칙에 맞게 의미 단위로 커밋하고 대상 PR 브랜치에 일반 push한다. 수정점별 인라인 URL, 수정 내용, 커밋과 검증 결과를 연결해 기록한다.
4. 1차라면 수정 후 head를 고정하고 새로운 리뷰어 2명으로 2차의 전체 절차를 반복한다. 수정이 없으면 같은 head로 2차를 진행한다.
5. 2차에서도 확인된 문제를 수정하고 검증한다. 자동으로 3차 리뷰를 추가하지 않는다. 2차 검토 SHA와 수정 후 최종 SHA가 다르면 최종 코드는 추가 독립 리뷰를 받지 않았다고 명시한다.

검증 실패나 미수정 항목을 숨기지 않는다. 같은 수정 시도를 새 근거 없이 반복하거나 실패한 검증을 통과로 간주하지 않는다.

## 최종 보고

PR 링크와 사용한 모델/설정, 차수별 리뷰어 2명의 완료 여부를 표시한다. 두 차수는 반드시 아래와 같은 동일 형식으로 보고한다. 수정점이 여러 개면 차수 안에서 항목별로 대응시킨다.

| 차수 | 발견한 수정점 | 어떻게 고쳤는지 | 검증 결과 | PR 인라인 리뷰 |
| --- | --- | --- | --- | --- |
| 1차 | 문제와 발생 조건, 또는 없음 | 수정 내용과 커밋, 또는 변경 없음 | 실행 결과와 미검증 범위 | 게시한 리뷰/스레드 링크, 또는 게시 없음 |
| 2차 | 문제와 발생 조건, 또는 없음 | 수정 내용과 커밋, 또는 변경 없음 | 실행 결과와 미검증 범위 | 게시한 리뷰/스레드 링크, 또는 게시 없음 |

차수별 검토 SHA와 최종 head SHA, 남은 문제나 게시 실패를 함께 적는다. 수정하지 않은 후보를 수정 완료 목록에 넣지 않고, 발견 사항 없음과 검토하지 못함을 구별한다.
