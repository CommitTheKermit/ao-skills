# Intent First

<!-- usage-stats: skill intent-first -->

첫 동작으로 `python3 "$HOME/.agents/skills/usage-stats/scripts/usage_stats.py" record skill intent-first >/dev/null 2>&1 || true`를 이 발동에서 한 번만 실행한다.

코드의 길이나 영리함보다 사용자가 하려는 행동, 기대 결과, 실패 이유가 코드에서 그대로 읽히게 한다. 사용자의 명시적 요구와 저장소 규약이 이 스킬보다 우선한다.

## 구현 전

1. 해결하려는 사용자 문제를 한 문장으로 재진술한다.
2. 사용자의 행동, 성공 결과, 실패 이유, 지켜야 할 정책을 식별한다.
3. 관련 흐름과 호출부를 읽고 코드베이스에 이미 쓰이는 도메인 언어와 책임 경계를 찾는다.
4. 결과를 바꿀 미확정 사항이 있으면 구현 전에 질문한다.

## 판단 순서

다음 순서로 가장 직접적인 표현을 선택한다.

1. 사용자와 기획자가 쓰는 용어를 타입, 함수, 변수 이름에 사용한다.
2. 같은 의도를 표현하는 기존 타입과 패턴이 있으면 재사용한다.
3. 조건식에 숨은 정책은 의도를 말하는 함수나 정책 객체로 드러낸다.
4. 성공과 실패 이유가 후속 행동을 바꾸면 `Boolean` 대신 명시적인 결과 타입으로 표현한다.
5. 유스케이스 하나는 가능한 한 사용자 행동 하나를 나타내게 한다.
6. UI, API, 데이터베이스 형식이 도메인 규칙의 이름과 구조를 결정하지 않게 한다.
7. 새 추상화는 현재 요구사항의 의미를 더 분명하게 만들 때만 추가한다.

짧은 코드와 의도가 분명한 코드가 충돌하면 의도가 분명한 쪽을 택한다. 다만 이름만 다른 전달 계층, 구현 하나뿐인 인터페이스, 미래를 위한 확장 지점처럼 현재 의도를 설명하지 않는 구조는 만들지 않는다.

## 코드 형태

- `process`, `handle`, `data`, `flag`, `isValid`처럼 문맥 없는 이름을 사용자 행동이나 판단 기준으로 바꾼다.
- 매직 값과 복합 조건에는 그 값이 존재하는 사용자 정책의 이름을 붙인다.
- 예외나 오류 코드는 기술 실패뿐 아니라 사용자가 다음에 무엇을 할 수 있는지 구분한다.
- 주석은 코드로 표현할 수 없는 결정 이유와 제약만 설명한다. 코드가 무엇을 하는지는 이름과 구조로 표현한다.
- 객체의 책임이 사용자 개념과 어긋나거나 객체지향 법칙을 위반하면 구현이나 리뷰 결과에서 구체적으로 밝힌다.

## 검증

변경 후 다음을 확인한다.

- 공개 타입과 함수 이름만 읽어도 사용자 행동과 결과를 설명할 수 있는가
- 핵심 정책이 익명 조건문, `Boolean`, 범용 예외 안에 숨지 않았는가
- 테스트 이름이 요구사항 문장으로 읽히며 성공과 주요 실패 이유를 검증하는가
- 기술 계층을 바꿔도 도메인 규칙의 이름과 의미가 유지되는가
- 새 구조가 현재 요구사항을 설명하는 데 실제로 필요한가

관련 테스트 또는 가장 작은 실행 검증을 수행한다. 검증하지 못한 부분은 완료로 표현하지 않는다.

## 보고

변경한 파일 목록보다 코드에 드러낸 사용자 행동, 정책, 결과를 먼저 설명한다. 의도를 위해 더 명시적인 타입이나 구조를 선택했다면 어떤 모호함을 없앴는지 짧게 밝힌다.
